# E-Commerce Sales Analytics Using Apache Spark

A full-stack college project: **PySpark** cleans an e-commerce order dataset and computes analytics with **Spark SQL**;
an **Express** API serves the results; a **React + Recharts** dashboard displays them. The default is **local Spark
mode** (no paid services). Optional **Amazon S3** storage and **Amazon EC2** deployment are configured through
environment variables and do not replace the local workflow.

> The bundled dataset is **synthetic** (generated by `spark-engine/generate_data.py`, fixed seed, fictional brands). It deliberately contains
> dirty rows and duplicates so the cleaning stage has real work. Numbers on the dashboard describe this synthetic data, not a real business.

## Features
| Area | What you get |
|---|---|
| Overview | Gross revenue, net revenue (after discounts), valid orders, units sold, average order value, purchasing customers, daily/monthly trend |
| Products | Top 10 by revenue, top 10 by quantity, revenue by category, low performers (includes zero-sale products via a LEFT JOIN) |
| Customers | Top spenders, repeat vs one-time buyers, RFM segmentation |
| Geography | Revenue by city and by state |
| Payments | Orders, revenue and share per payment method |
| Data quality | Input / valid / rejected / duplicate counts, rejection reasons, status breakdown, processing status |
| Dashboard | Sidebar navigation, date-range + category + city filters with reset, INR formatting, loading / error / empty states, responsive layout, light/dark theme, **CSV export** of every result table |

## Architecture
```
local CSV  or  s3a://$S3_BUCKET/raw/orders.csv
      │
      ▼
PySpark ETL  (spark-engine/jobs/cleaning.py)      trim → de-duplicate → validate → derive revenue columns
      │
      ▼
Spark DataFrames + Spark SQL (jobs/aggregations.py)   joins, window functions, aggregations
      │
      ├── batch job  (analytics.py)  → output/*.json   (+ optional copy to s3://…/processed/)
      └── worker     (worker.py)     → ONE long-lived Spark session answering filtered queries
      │
      ▼
Node.js + Express REST API (backend/)   reads local JSON (hydrates from S3 on boot if configured)
      │
      ▼
React + Vite + Recharts dashboard (frontend/)
```
**Why a worker?** Date/category/city filters change distinct counts (orders, customers), which cannot be derived by adding
up precomputed totals. So filtered requests are answered by Spark too: a single Spark session (started once, data cached in
memory) answers them over stdin/stdout. Results are cached per filter combination. No Spark session is started per chart request,
and **Node performs no analytics** — it only validates input, routes and formats (CSV).

## Setup and run
See **START.md** for exact commands (macOS/Linux and Windows). Short version:
```bash
python3 -m venv .venv && source .venv/bin/activate
pip install -r spark-engine/requirements.txt
python spark-engine/generate_data.py            # dataset (use --orders N / --seed S to change)
python spark-engine/analytics.py batch          # Spark processing -> output/
(cd backend && npm install && npm start)        # API  :4000
(cd frontend && npm install && npm run dev)     # UI   :5173
```

## Amazon S3 (optional)

Keep **Block Public Access** on. Spark reads the CSV with Hadoop S3A (`s3a://`). JSON reports are written locally for the API and copied with boto3 using the default credential chain (shared config, environment, or EC2 instance profile). Hadoop AWS packages are added only when S3 is enabled: Spark 4.x uses `org.apache.hadoop:hadoop-aws:3.4.1`; Spark 3.5.x uses `hadoop-aws:3.3.4` plus `aws-java-sdk-bundle:1.12.262`.

```bash
# 1. Create a private bucket in the AWS console (this project will not create it for you).
# 2. Upload the dataset
python spark-engine/upload_dataset.py
# 3. Verify access (fails clearly on missing bucket, bad credentials, or network errors)
python spark-engine/s3_cli.py check
# 4. Run Spark SQL against S3
#    (Linux/EC2 recommended; Windows S3A often needs extra Hadoop/winutils setup)
DATA_SOURCE=s3 S3_BUCKET=your-bucket AWS_REGION=ap-south-1 python spark-engine/analytics.py batch
```

On Windows PowerShell, set the same variables with `$env:DATA_SOURCE='s3'` (see START.md). Local mode is unchanged: omit `DATA_SOURCE` or set it to `local`.

## Business rules (how the numbers are calculated)
* **Gross line revenue** = quantity × unit price. **Discount amount** = gross × discount rate. **Net line revenue** = gross − discount amount.
* **Average order value** = total net revenue ÷ number of **distinct** valid orders (an order with several lines counts once).
* **Discount representation:** a fraction between 0 and 1 (0.10 = 10 %). Empty = no discount. Values such as `10` or `1.5` are **rejected**, not guessed.
* **Duplicates:** exact duplicate rows (after trimming) are removed; the first copy is kept.
* **Rejected records** fail one of: missing order/customer/product ID, invalid or out-of-range date (before 2000 or in the future), quantity not a whole number ≥ 1, unit price not in (0, 1e9), discount outside 0–1, unknown order status. The first failing rule is recorded.
* **Cancellations and returns:** `Cancelled` and `Returned` rows are *valid* records but are **excluded** from revenue, orders, units and customers. The Overview page reports how many orders and how much order value were excluded. Only `Delivered` and `Shipped` count as sales.
* **Normalisation:** whitespace trimmed, status/payment method case-insensitive (` delivered ` → `Delivered`), `Canceled` → `Cancelled`, city/state title-cased, missing category → `Uncategorized`.
* **Filters:** date range, category and city are applied to order lines. With a category filter, *orders* means distinct orders containing at least one line of that category and AOV is that category's net revenue ÷ those orders.
* **RFM:** recency = days since the customer's last order (relative to the last order in the selection), frequency = distinct orders, monetary = net revenue. R and M are scored 1–5 with `NTILE(5)`; F uses fixed thresholds (1, 2, 3, 4–5, 6+). Segments, in priority order: Champions (R≥4, F≥4), Loyal (F≥4), Potential Loyalists (R≥3, F≥2), New (R≥4, F=1), At Risk (R≤2, F≥2), Hibernating (R≤2, F=1), otherwise Needs Attention.
* Profit, margin and customer lifetime value are **not** calculated: the data has no cost information.

Supported input columns: `order_id, customer_id, product_id, order_date (YYYY-MM-DD), quantity, unit_price, order_status` (required) and
`product_name, category, discount, payment_method, city, state` (optional; defaults are filled in).

## API
All responses: `{ "success": true, "data": …, "meta": { "filters", "generated_at", "source" } }`; errors: `{ "success": false, "error": { "code", "message" } }`.

| Method & path | Description |
|---|---|
| `GET /api/health` | Liveness check (`data_source` local/s3; no secrets) |
| `GET /api/status` | Spark job state (`idle/running/succeeded/failed`) and whether results exist |
| `POST /api/jobs/run` | Start the PySpark batch job (202; 409 if already running) |
| `GET /api/filters` | Categories, cities and the dataset's date range |
| `GET /api/overview` | KPIs + excluded (cancelled/returned) summary |
| `GET /api/trends` | `daily[]` and `monthly[]` revenue/orders/units |
| `GET /api/products` | `top_by_revenue`, `top_by_quantity`, `by_category`, `low_performers` |
| `GET /api/customers` | `top_spenders`, `repeat_vs_onetime`, `rfm_segments` |
| `GET /api/geography` | `by_city`, `by_state` |
| `GET /api/payments` | Per payment method |
| `GET /api/data-quality` | ETL quality report (always for the whole file; filters do not apply) |
| `GET /api/export/:dataset` | CSV download: `daily_trend, monthly_trend, top_products_by_revenue, top_products_by_quantity, category_revenue, low_performing_products, top_customers, repeat_vs_onetime, rfm_segments, city_revenue, state_revenue, payment_methods` |

Filter query parameters (analytics + export): `start`, `end` (`YYYY-MM-DD`), `category`, `city`. Example: `/api/overview?start=2025-01-01&end=2025-06-30&category=Books`.

### What has and has not been verified
Verified in the build environment (Linux, Java 21, Python 3.13, Node 22): the pytest suite (7 passed), the backend integration suite (8 passed),
a full Spark batch run on 112,080 rows (about 51 s, input = duplicates + rejected + valid balanced), the API through the Vite proxy
(including a filtered, Spark-computed request and CSV export), and a successful `vite build`.
**Not verified:** how the dashboard *looks* in a browser (no browser was available — please review the UI yourself), and Windows/macOS or Java 11 / PySpark 3.5 runs.

## Known limitations
* First batch run takes about a minute; a new filter combination takes roughly 10–15 s (then it is cached). The worker keeps ~1–2 GB of RAM.
* Local mode on one machine. The same code would run on a cluster, but that was not set up or tested.
* Data is synthetic; business conclusions cannot be drawn from it.
* The dashboard uses the API's filter lists; unusually large category/city lists would need a searchable control.
* No authentication (out of scope). If you put the dashboard on the public internet, put TLS (nginx) in front and restrict SSH; this is still not a hardened multi-tenant product.
* Windows: Spark reads a **local** CSV without Hadoop `winutils`. Direct `s3a://` reads are intended for Linux/EC2. Use `DATA_SOURCE=local` on Windows unless you have a working Hadoop/S3A setup.
* Troubleshooting: `JAVA_HOME is not set` → install JDK 17/21 and set it; "Could not start Python" → create `.venv` or set `PYTHON_BIN`; port busy → change `PORT`; S3 errors → `python spark-engine/s3_cli.py check`.
